# Requirement discovery and behavioral comparison (#51)

Use this procedure only for evaluated repository changes that warrant it. Small tasks need no map or comparison run. The executing agent, not the evaluator, discovers the task's requirements; a completed model reply is not verified success (v0 §3). This document does not authorize model spending, a Rust port, or running untrusted candidate code on the host.

## Discover before changing

Pin the reference Git commit and executable digest. Keep its checkout, reference observations, and evaluator cases outside the candidate's writable output. Inspect governing docs, source, public interfaces, existing tests, and actual build/test commands. Group *behaviors* into scenario families (including errors, permissions, cancellation, native continuation and filesystem effects when relevant), not Go private helper names. Record source/test evidence with paths, observed lines and whole-file SHA-256; explain spec/code disagreements, old bugs and gaps rather than silently treating any one source as normative. Produce the requirements-to-tests map before translating or editing tests. For every requirement give its behavior, evidence, family, relevant test or gap, and `retained`, `ported`, `replaced`, or `excluded` disposition with a reason for exclusions. Candidate tests do not become the independent oracle.

Run the pinned reference build and tests, retaining the exact argv, exit status, full output log and its digest. A failed, skipped or absent required reference check makes comparison invalid, not a candidate regression. A protected task-specific producer (for example a scripted CLI run or local fake-provider test) captures observations for reference and candidate against the **same** evaluator-owned case IDs and inputs. Native/provider items are compared as bytes, not reparsed into normalized JSON. Retain source and executable hashes with the observation set. Re-run affected checks/cases if relevant source, tests or fixture inputs change. The evaluator cases, expectations and baseline logs must not be in the agent-writable candidate tree. The comparator validates records; it cannot prove their provenance or confine a candidate process. #53 will supply protected execution, full-tree capture and a task runner for agent-written code.

A re:agent producer can run `reagent run --scripted FILE --trace-file PATH` for deterministic tool cases, or use the existing local fake-provider tests for HTTP/native cases. Preserve CLI stdout/stderr as raw bytes. Collect ordered `model.accepted` calls (including exact argument strings), their `tool.finished` outcome codes/effects, and `run.finished.status` from the private JSONL trace (v0 §7); watch file bytes/modes independently. Where byte-identical native continuation matters, use captured exact `api.attempt` bodies or the local fake provider's bytes, not reserialized normalized `model.accepted.native.items`. The runtime trace is best effort, but an evaluator missing a required event or file observation must emit `incomplete`, never infer success. Raw traces include prompts and file contents and are not comparison reports or safe publication artifacts.

## Offline record contract

`python3 bench/behavior.py --manifest CASES.json --map MAP.json --links LINKS.json --reference REF.json --candidate CAND.json --reference-root REF_DIR --candidate-root CAND_DIR --reference-binary REF_BIN --candidate-binary CAND_BIN --candidate-snapshot SHA256 --out REPORT.json` reads records only, never runs the candidate. Paths to manifest, map, evaluator links, records, reference root/binary, baseline logs and report must be outside `CAND_DIR`. It checks that `REF_DIR` is a clean checkout at the full `REF.json.source_revision`. The evaluator manifest and observation records use `version: 1`; SHA-256 values are lowercase hex. The operator produces records with actual commands, not model assertions.

- Evaluator manifest: `required_families` and nonempty `cases`. Each case has unique `id`, `family`, `input` (`argv` strings, canonical `stdin_b64`, and workspace-relative fixture `files` with `content_b64`), and `watch` (relative paths observed even if absent); optional `normalize_stderr_workspace: true`, `require_native: true`, or `require_calls: true` for cases where absent provider bytes or tool calls invalidate evidence. All manifest cases are required. Do not give evaluator answers or hidden case IDs to the discovering agent. After the map is produced, an independent evaluator supplies `LINKS.json` (`version: 1`, pinned `source_revision`, and one `cases` entry per hidden case with its `id` and the discovered requirement IDs it tests). The comparator checks every case has a non-excluded, non-gap link; the human evaluator checks that each link's behavior really fits.
- Agent-produced map: `source_revision` and `requirements` with unique `id`, nonblank `behavior`, `families`, `sources` (`path`, one-based `line`, whole-file `sha256`), `test` (path/command, or `gap: ...`), `disposition` and, for `excluded`, nonblank `reason`. Required cases linked to an exclusion or test gap, or cases without an independent link, are `incomplete`; source references are checked against the pinned reference bytes. Syntactic evidence is not proof the claim is semantically correct.
- Reference record: `source_revision`, `binary_sha256`, `snapshot_id`, `baseline_checks` (unique `name`, `argv`, `exit_code`, `log_path`, `log_sha256`; `build` and `test` required) and `cases`. Candidate record: `binary_sha256`, `snapshot_id` matching the CLI argument, and `cases`. Both binaries are checked against their recorded digests. A producer must bind every case to the same recorded snapshot and include all changed files as well as the declared watched files; #53 will establish and verify complete-tree provenance.
- Each case observation has `id`, `input_sha256` (SHA-256 over compact, sorted-key JSON of the evaluator's `input`), absolute `workspace`, integer `exit_code`, `status` (runtime status or `not_applicable`), exact `stdout_b64` and `stderr_b64`, ordered `calls` (each `name`, exact argument string, outcome `code`, `effect`), ordered `native_items` (each `provider`, exact `raw_b64`), and `files` (unique relative `path` plus `present`, and when present numeric `mode` and byte `sha256`). Base64 is canonical, so text decoding cannot discard bytes. The comparator compares all these substantive fields in order, including extra changed files. It never accepts a missing required observation as a match.

Comparison is exact by default. The **only** built-in normalization is an evaluator case's explicit replacement of that side's temporary workspace-root bytes with `<workspace>` in **stderr**. Do not normalize stdout, errors/exit codes, ordering, arguments, effects, file digests or native bytes. If another difference is intentionally acceptable, document it and supply a task-specific producer/oracle; do not weaken this common comparator. The report gives `pass`, `behavior_difference` with case/field references, `incomplete` for missing candidate/map evidence, or `invalid_reference` for failed/missing reference evidence. It contains no raw prompts, source or file bytes. `completed` is an observed status, never the report's correctness verdict.

The two evaluator manifests in `testdata/behavior/` exercise this same record format on an ordinary refactor-shaped example and a tiny cross-language migration-shaped example. The offline tests run trusted toy Go/Python programs and incorrect variants, then compare captured observations; they do **not** demonstrate model-led discovery or a Rust port. The Rust pilot and any full self-migration still need separate authorization and evidence (`docs/reagent-rust-challenge.md`).
