# re:agent v0 — Design

**Status:** Current specification. It states the rules as they are now. Reasons and evidence for a change live in its PR, not here; the dated amendment history up to 2026-10-02 is in `docs/archive/reagent-v0-design-2026-10-02.md`.
**Reference target:** `docs/reagent-v1-design.md`. A reference such as **v1 §5.3** adopts only what this document selects. On conflict, v0 wins. MUST marks required behavior. Do not implement deferred v1 requirements because v1 already specifies them.

## 1. Objective and scope

A small agent whose every decision can be read in its code and its actual model requests. Go, direct provider HTTP (no SDK, no agent framework, no Codex wrapper — final), native function tools, locally owned complete history with provider-native items preserved, sequential dispatch, a pure context builder, and JSONL traces of exact request/response bytes.

One executable: `run` (one task) and `chat` (a conversation). Tools: three read tools, three file writers, `exec`, two workspace tools, an optional friction reporter, and the experimental `git_do`. A scripted model and a fake `echo` tool exercise orchestration without a key. No service, plugin system, or extensibility framework.

## 2. Structure and adopted contracts

`cmd/reagent` plus one `internal/reagent` package, one concern per file.

| Component | From v1 | Scope |
|---|---|---|
| Model interface | §5.1 | `Name`, `Generate`; I/O separate from execution |
| Transcript | §5.2 | User, assistant, tool, shell and summary entries; ordered blocks; call IDs; argument strings; provider-tagged native items |
| Tools and results | §5.3 | Spec/implementation boundary; one outcome envelope for every tool |
| Loop | §7.2; §7.3 items 1–6 | Control flow and response precedence |
| Context | §8.1; §8.4 | Pure construction; complete history |
| Operating modes | §10.3 | Read, write and exec by default; `--read-only` withholds write and exec; plan mode (§10.3 here) withholds them further |
| Live request/decoding | §9.1–§9.5 | Direct transport, native tools, complete-response normalization, native continuation |

Omit exhibits, replay metadata, schema/prompt version bookkeeping and accounting for unaccounted attempts. Keep response IDs and returned usage. Each tool's description and schema have one source; native declarations are built from it, never duplicated into a prompt template.

## 3. Invariants and loop

Adopt v1 §6.3 invariants I01–I12, I15 and I17 unchanged; tests cite their IDs. `completed` means the model gave a final reply, not that the task succeeded; every summary keeps that distinction. A task is **verified** only when its required checks passed on the stated revision and snapshot, required independent findings were resolved, and no required evidence is missing or skipped; otherwise report the blocker without changing the Run status.

| Deferred | v0 treatment | Restored by |
|---|---|---|
| I13 | Trace writes are best effort | v1 §16.5 |
| I14 | No replay | v1 §17 |
| I16 | No tool-retry subsystem; I05 still governs every accepted call | v1 §§6.3, 9.6, 19.3 |
| I18 | No general uncertain-effect recovery; §9's exec rule is the exception | v1 §§7.5, 15.3, 19.3 |

Never execute an accepted call twice. No automatic tool retry. Returned model usage, when known, is counted even if the response fails protocol validation: the tokens were spent.

The loop is one function. Budgets are `max_steps` and `max_tool_calls`; both default to unlimited (0). A positive value keeps v1 §7.4's whole-batch and follow-up-step reservation; invalid or denied calls consume the call budget; negative is invalid. HTTP attempts are counted but are not a budget for ordinary runs. No ordinary response call cap, run deadline or token budget. §3's opt-in child bounds are the narrow exception.

Stop reasons stay distinct (I11): completed, refused, cancelled, provider error, incomplete response, protocol error, limit exceeded (budget exhaustion, request size, context overflow, each with its own reason), effect unknown, tool internal error, persistence error (§10.8). Malformed arguments in a valid call envelope are an observation; an incomplete response or duplicate call ID is a protocol stop.

**Session and Run.** A Session holds what outlives a run: fixed configuration, accepted transcript, every accepted call ID (I04 spans the session), workspace grants. A Run holds its ID, counters, effects and trace. Only `completed` and `refused` runs leave the session continuable (v1 §7.5), with one exception: a run that stops with `provider_error` or `cancelled` at a model request, during routing, or before the next request leaves the transcript where that request was built from, so it is marked `resumable` and the next message continues. Every other outcome blocks until `/reset` or a successful `/compact`. `/reset` discards history, seen call IDs, blocking, the meter, the admission rate and usage, and keeps the current model and effort, workspace selection and grants, plan mode and the Auto setting; it never rewrites the old transcript.

**Fresh-context children.** `--child-runs` is off by default, retained on chat resume and fresh model switches, and registers one synchronous read-class `child_run` tool. One parent Run may start at most four one-level children; each gets a fresh Session/Run with six steps, twelve calls, and only read tools over an explicit frozen UTF-8 snapshot. Snapshot manifests contain 1–20 workspace-relative paths with exact SHA-256 digests, at most 4 MiB total; the first accepted capture returns an ID that later children in that Run may reuse to see identical bytes. A child receives its own fixed embedded read-only instructions (not parent-only command, mutation or workspace-state instructions), the selected workspace's fixed project rules, and its own read-only runtime. Its initial history has exactly one user entry with kind (review or research), task, specification and manifest identity; a report correction may add one later (§3). It never receives the parent transcript, workspace observation, provider-native items, compaction summary, author rationale, siblings, or traces. The child has no workspace switching, exec, writing, Git, routing, compaction or delegation; it cannot expand the parent's mode, plan setting or grants. Files are staged in a private temporary directory and removed after the child exits. Credentials stay in the adapter. Child counts and results are observations, not verified approval.

A parent Run shares an aggregate child allowance of 24 steps, 48 calls, 48 actual HTTP attempts and ten minutes from the first child launch. Admission also stops after 200,000 reported input-plus-output tokens; usage is reported separately and unknown remains unknown. This is not a hard token or cost cap: a reply may exceed the threshold before usage is received. Child attempts are admitted at the transport send boundary; unsuccessful children and denied calls do not reset allowances. The initial child task states the exact report JSON schema and limits. A completed child must return a text-only JSON report with required nonblank summary (≤4 KiB), required findings array of at most 20 entries (each requires severity ≤32 bytes, location ≤256 bytes, description ≤1024 bytes), and required verdict `concerns`, `no_findings`, or `inconclusive`; no extra fields, total reply ≤16 KiB. The validator accepts either bare JSON, one enclosing `json`/plain code fence, or one introductory sentence ending in `:` or `.` on its own line (≤160 bytes), not combinations or trailing prose. An invalid final reply gets exactly one correction user entry within the same child Run, subject to its remaining step/time/usage/attempt bounds; a second invalid reply is a protocol error, and no remaining step is `limit_exceeded`. No tool is replayed. Missing/malformed reports, refusal, failure, cancellation, exhaustion and cleanup failure are not approval. The result includes status/reason, report validity, snapshot and child Session/Run/trace IDs, steps/calls/attempts and usage. Cancellation propagates without restarting work. Runtime `completed` still does not imply task success.

## 4. Byte limits and file access

```go
MaxFileBytes    = 1 << 20  // one file snapshot
MaxResultBytes  = 32 << 10 // one encoded tool outcome
MaxRequestBytes = 10 << 20 // one encoded model request; a local sanity cap, not a cost control
```

Other controls are named where they apply (§6 timeouts, §9 exec timeout, §3 budgets); do not grow a general bounds table.

Read files through a limit-plus-one reader. Adopt v1 §11.3's text, digest, line-numbering and complete-element conventions without its per-line cap; a line that cannot fit is an explicit error. One shared fit-to-budget helper appends complete elements until the encoded outcome would exceed `MaxResultBytes`; result truncation satisfies I12.

**Paths.** An empty path is the active root. An absolute path is accepted only if its cleaned relative form stays inside the root. Reject NUL, `..` components, and withheld names: `.git` (case-insensitive), `.env` and `.env.*` (lowercased). Listing and search omit withheld names. Walking does not follow directory symlinks; writers reject symlink leaves. Keep v1 §11.2's ordering and search exclusions; no `.gitignore` parsing. These are ordinary checks, not a sandbox, and not race-proof; `exec` is not bound by them.

**Workspaces.** The launch root is approved. A session may hold more exact canonical roots or prospective destinations (an exact non-symlink child of an existing parent), approved only by the human (§10.5). An approved root covers its descendants, never its parent or siblings. Tools act on the one active root. Canonicalize roots; check resolved existing targets (or existing parents, for creation) by path-component containment and withheld names. Refuse filesystem roots, withheld locations and parent traversal. Git relationship grants nothing; linked worktrees are validated with bounded offline Git plumbing, comparing directories with `os.SameFile`.

## 5. Read tools and argument validation

| Tool | v1 contract | v0 arguments |
|---|---|---|
| `list_files` | §12.1 | `path` required; `offset` default 0; omitted `limit` = as many as fit |
| `read_file` | §12.2 | `path` required; `start_line` default 1; omitted `max_lines` = 250, still fit to result budget |
| `search_text` | §12.3 | `query` and exactly one of `path` or `paths` (1–20 strings) required; search in path order, deduplicating files across overlapping paths with one shared result budget and `max_results`; literal case-sensitive by default; `regex: true` uses Go RE2 per line (reject non-compiling, empty-matching, or null); omitted `max_results` = as many as fit; a literal query containing `\|` that matches nothing says so in the outcome message and suggests `regex: true` |

Counts are positive when given, offsets nonnegative. An oversized search match is shortened with `preview_truncated`; a byte-limited or skipping search reports `complete: false`. Descriptions state the v0 defaults and claim no v1 maxima.

Arguments: typed decoding of exactly one JSON object, required fields, unknown-field rejection, explicit semantic checks before execution; null is not omission. Declare tools with `strict: false`.

## 6. Context and the live adapter

`BuildContext` is pure: it receives state and returns a request; all reads (files, Git, clock) happen before it. One encoder per provider, `EncodeRequest`, is used by both the live path and previews.

**Instructions** are, in order: the fixed embedded instructions (a separate fixed read-only text for §3's children), a runtime section, the optional friction paragraph (§10.7), then project instructions. The runtime section holds only session-fixed facts: mode, active workspace, provider, requested model, effort, platform, budgets. Nothing that changes per request (a counter, a clock) may enter the instructions, because providers cache the prefix byte for byte.

**Project instructions.** At launch, read only the workspace root's `AGENTS.md` (no parent or nested search): at most 32 KiB of UTF-8, else skipped with a one-line warning, never truncated; a root symlink loads only if its regular-file target is inside the root and not withheld; check the file type before opening. `--no-project-instructions` disables it. The copy is fixed for the session and reloaded only on an actual workspace switch.

**Per-turn snapshot.** Each user entry carries a `workspace_state` collected before the run: local date and zone, canonical workspace, and when Git is available, branch, upstream and divergence, default branch (`origin/HEAD`, else `origin/main` if `rev-list` succeeds) and divergence, last fetch, and staged/modified/untracked counts. Probes run in the root with the child environment, empty stdin, `-c core.fsmonitor=false`, a two-second deadline, output bounded by `MaxResultBytes`, no network. When read-only or plan mode forbids execution and the active root is not the launch root, use ref plumbing only (no `status`) and mark `counts: "omitted in read-only/plan mode"`. Failed observations are omitted. Encoders send it as a second text part of the user message; it is data, not authority.

**Providers.** OpenAI Responses and Anthropic Messages. The transcript stays provider-tagged and each encoder refuses the other's native items. Normalized blocks drive runtime decisions; native items continue the provider's own conversation and are never duplicated as text.
- *OpenAI:* `store: false`, `include: reasoning.encrypted_content`, `truncation: "disabled"`, `parallel_tool_calls: true` (dispatch stays sequential). Catalog models send `text.verbosity: "low"`; unknown models send none. Every request carries `prompt_cache_key`: the first 32 hex digits of SHA-256 over model, instructions, tool names and schemas, and the first history entry without its snapshot.
- *Anthropic:* a fixed output ceiling (`anthropicMaxTokens`); cache breakpoints on the system block and on the last block of the last message; a stop-reason refusal becomes a refusal block; cached tokens are summed into input. Adjacent user content (text, shell records, summaries, results) is merged so roles alternate.
- *Proxy:* `API_PROXY_URL` (full endpoint) and `API_PROXY_PROVIDER=openai` together route OpenAI requests to a proxy. No `Authorization` header and no key is sent. The proxied form differs in exactly: `stream: true`, `truncation` omitted, and a `session-id` header equal to `prompt_cache_key`. The SSE reply is rebuilt into the non-streamed body before use; nothing is displayed as it arrives: `response.completed` output, else `output_item.done` items by index; `response.failed`/`error` events are provider errors (read both top-level and nested `error` shapes); `response.incomplete` or a stream ending without a final event is incomplete. The header, `/status` and `/model` name the proxy; traces mask any password in its URL.

**Effort.** `--reasoning-effort auto` uses the catalog model's default, else `low` for OpenAI and none for Anthropic; empty omits the parameter; an explicit value passes through unchecked. The catalog (`catalog.go`) is a fixed list of models with provider, efforts, default effort, verbosity and known context window; `--model` still accepts any name.

**Timeouts.** Waiting for response headers is bounded by `ResponseHeaderTimeout` (10 min); after headers, each body read must bring data within `ResponseIdleTimeout` (5 min). No total bound on a reply that keeps arriving. Expiry is a transport error, not retried. Ctrl-C cancels at any point.

**Context overflow.** An HTTP 400 `context_length_exceeded` / `prompt is too long`, or the same code in a streamed `response.failed` or `error` event, becomes `limit_exceeded` with reason `the conversation no longer fits the model's context window`, keeping reported usage.

### 6.1 `--show-context`

`run --show-context` writes the exact step-one request body to stdout and exits 0, using the same builder, encoder and size check as the live path, without a key, network, tools or trace. With fixed input it is byte-identical to the first live request (including `prompt_cache_key` and the proxied form). It never contains credentials. `/context` in chat measures the next request the same way.

### 6.2 Retry policy

At most two HTTP attempts per step. Retry only 429 and 5xx, after a fixed cancellable 500 ms, with the identical body. Transport/read errors, timeouts, other statuses, incomplete or invalid output, and in-stream errors (including overloads) stop the call. Every attempt is traced. The loop never adds another retry.

Children build their first request from only the child user entry and fixed instructions; their own read-only snapshot workspace and project rules are fixed at launch. No parent state is projected into a child model request (§3).

## 7. JSONL trace

Adopt v1 §§16.2 and 16.4: exact prepared request bytes and exact response bytes, as JSON strings; a non-UTF-8 response is stored with replacement and `body_utf8_replaced: true`. One file per run (or per compaction or switch attempt) under the v1 §16.1 location; `--trace-file` (run) or `--trace-dir` (chat) override it. Files are created exclusively, directories 0700 and files 0600: traces hold prompts and file contents. Creation or write failure warns once and the run continues (I13 deferred).

Each child has a separate best-effort run trace. The parent trace carries the child tool arguments and bounded outcome, never a child history or the child's API request bytes.

Events: `run.started` (resolved nonsecret options, instructions, prompt, tools, the `initial_history` it began from, `build`, active workspace), `model.requested`, `model.accepted`/`model.failed`, `api.attempt.started`/`finished`, `tool.started` (only immediately before a real implementation runs) and `tool.finished`, `run.finished` (with `resumable` when set), `compaction.requested`/`finished`/`failed`, `model.switch.requested`/`finished`/`failed`, and `auto.route`. Tool outcomes, shell records and effect records carry their workspace. No credentials, no child environment, no duplicate copy of the transcript in switch or routing events. The emitted fields and jq recipes are in `docs/reagent-trace-format.md`. Read traces with `jq`; there is no trace reader.

## 8. File writers

All require write authority, use §4's path rules, reject symlink leaves and directories, read one snapshot under `MaxFileBytes`, and publish by writing a sibling temp file and renaming (permissions preserved). Errors before publication have `effect: none`; publication is `effect: applied`.

- `edit_file(path, expected_sha256?, old_text, new_text | edits?, append_text?)`: either one `old_text`/`new_text` pair or a nonempty `edits` array of required `{old_text, new_text}` pairs with optional per-edit `replace_all` boolean, but not both; `append_text` may stand alone or accompany either form and adds bytes at the end without an implicit newline. Each nonempty `old_text` must occur exactly once in the digest-checked snapshot (overlap-aware), except `replace_all` replaces every non-overlapping occurrence (at least one required). Identity edits still require a unique match and are skipped, with their indexed skips reported in result data; a call whose every edit is an identity edit is `invalid_arguments`. Matched ranges across the entire batch, including skipped edits, must not overlap. Apply all replacements against that snapshot, then append; any invalid edit, oversized result or NUL fails without publication. Empty `append_text` and no change are `invalid_arguments`; errors for an array edit name its index. Publish once, return the total replacement count, per-edit replacement counts (zero for skipped edits), and appended byte count when nonzero, and remember one new digest. Ambiguous matches report up to ten start lines (including overlaps) and suggest `replace_all` when all should change; missing matches report up to five whitespace-normalized candidate lines, without applying a fuzzy match.
- `write_file(path, content, expected_sha256?)`: a missing target without a digest is created; create makes missing parent directories under the active root, mode 0755, outermost first, rejecting withheld components and symlinked or non-directory components along a missing parent path. An already-existing parent follows §4's resolved-path checks, including in-workspace symlinks. If file publication fails, remove only newly created directories that are still empty, deepest first. Report their workspace-relative paths in `created_dirs` when nonempty; create links a staged file exclusively, mode 0644. An existing regular file is overwritten with a supplied digest or the latest digest seen for it; a digest for a missing file is `not_found`. Content must be UTF-8 without NUL within `MaxFileBytes`. Returns `operation` create/overwrite, before/after digests, size.
- `delete_file(path, expected_sha256?)`: removes one existing regular file.

**Digests.** A supplied `expected_sha256` must be 64 lowercase hex characters, else `invalid_arguments`. A digest matching the current snapshot is accepted. On mismatch, one previously returned for that path by `read_file`, `edit_file` or `write_file` is `stale_file`; any other is `unknown_digest`, naming the current digest. When omitted for an existing target, the latest digest returned for its canonical path by those tools stands in: without one, `invalid_arguments` asks the model to read the file; if it differs from the current snapshot, `stale_file` names the current digest and asks for another read or an explicit digest. The check and change use the same snapshot. A ranged read counts; search and listing do not. A successful delete removes the seen digest. Reset and successful compaction clear seen digests across workspaces; model switches keep them, while newly opened workspaces and resumed sessions start empty. The set of returned digests used to classify explicit mismatches remains unchanged.

No directory creation outside `write_file` create, ordered patch format, multi-file patches, fuzzy matching, or rooted publication.

## 9. `exec`

Explicit `argv`, required `cwd` (an existing workspace-relative directory, `.` for the root, §4 path rules), optional `timeout_ms` (default 2 min; values under 10 s are raised to 10 s and the effective value reported). v1 §14.2's environment allowlist and empty stdin. `exec.CommandContext` with `WaitDelay = 1s`. On Linux and macOS, start the command in its own process group; on timeout/cancellation send TERM to the group, then KILL after 200 ms and reap the direct child. Capture stdout/stderr through owned pipes; after reaping the leader, allow one second for both readers to reach EOF. If either does not, kill the group and report unknown effects regardless of the leader's exit status. Do not use process-group liveness as a proxy for pipe completion: Linux zombies can keep a group visible after all output has closed. This adopts only v1 §14.3's cancellation group signaling for `exec`, reversing v0 §14's deferral; it does not change the human `!` shell or add general process-tree management. Children that deliberately leave the group are not supervised. stdout and stderr each go through a bounded writer that keeps the first and last halves of `MaxResultBytes` and counts all bytes; the combined outcome is then fitted to `MaxResultBytes` by removing from each stream's middle, streams separate, truncation marked with omitted byte counts at UTF-8 boundaries; if even the marker cannot be shortened, drop that stream rather than loop. `!` records use the same capture and trimming.

A nonzero exit is an ordinary error observation. Distinguish failure to start from an error after starting: wait/capture failures after start report `effect: unknown` and cannot be `process_start_failed`. A timeout, user cancellation of a started command, or inherited-pipe wait failure also reports `effect: unknown` and stops the run (§3); never retry a possibly applied command or claim cleanup outside the process group. Report an observed exit code/signal from the reaped child. `output_may_be_incomplete` marks a pipe that did not reach EOF; the separate stdout/stderr `truncated` flags mean only bytes trimmed by the result budget. Background descendants whose pipes have closed do not change an ordinary exit observation.

Optional `then` chains up to 7 more argument vectors, run in order in the same `cwd`, each only if the one before it succeeded, like `&&`; there is still no shell. Each command gets its own timeout and an equal share of `MaxResultBytes`. The data lists every step that ran as `steps` and the skipped vectors as `not_run`; the outcome takes the last step's code, its message names the failing step, and the effect is the strongest any step had. The fixed instructions show one `then` example.

## 10. CLI and chat

### 10.1 Commands and flags

`reagent run [flags] "prompt"`, `reagent chat [flags]`, `reagent help [run|chat]`, `reagent version`. A flag after a `run` prompt is refused; `--` passes flag-like text.

Shared flags: `--provider` (inferred from the model name; a contradiction is a startup error), `--model`, `--reasoning-effort`, `--auto`, `--workspace`, `--allow-workspace PATH` (repeatable), `--read-only`, `--plan`, `--no-project-instructions`, `--max-steps`, `--max-tool-calls`, `--in-run-compact`, `--child-runs`, `--recap`, `--report-friction`, `--git-do jev|recipe`, `--scripted FILE`. `run` only: `--prompt-file PATH|-` (one prompt source; only the final newline is removed), `--show-context`, `--trace-file`. `chat` only: `--trace-dir`.

Environment: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` (read for any non-preview run, since chat can change provider; each is sent only in its own provider's header, never to a proxy), `API_PROXY_URL`/`API_PROXY_PROVIDER`, `TYPESAFE_API_KEY` (read only when Auto or `--git-do jev` is on), `REAGENT_MODEL`, `NO_COLOR`. The binary never reads `.env`; `make live` sources it for the opt-in live tests only.

`--scripted FILE` replays a JSON array of normalized responses through the real dispatcher, registers `echo`, needs no key, and excludes `--provider`, `--model`, `--auto`, `--show-context` and `--child-runs`. Running out of responses is a protocol error.

Exit codes: 0 completed or preview; 1 noncompleted run or runtime error; 2 invalid CLI, configuration or input. A trace failure never changes the exit code.

### 10.2 Output

Replies go to stdout; headers, activity, status and summaries to stderr. While a chat input region is active, replies, activity, notes, summaries, context warnings, and `!` output are inserted above it. Replies use the region when stdout shares stderr's terminal; redirected stdout keeps the same bytes. The region stays visible during a turn, with progress in its status rows. Terminal control characters in model text are escaped (v1 §18.3) before any styling. On a styled terminal the reply is rendered as a Markdown subset with word wrap (≤ 100 columns) and aligned tables; pipes, redirects and `NO_COLOR` get the exact sanitized text. Display is derived from calls, outcomes and results and never feeds back into requests, transcript or trace. Successful read-tool calls are summarized in one line per turn; failures show individually. The effects recap shows for noncompleted runs, and for completed ones with `--recap`. The run summary prints input, cached and output tokens.

### 10.3 Chat input and modes

One submission per line on piped input. On a terminal, re:agent owns editing; `golang.org/x/term` supplies raw mode and size. In-memory history (≤ 500), bracketed paste as one submission, trailing `\` continues, Tab completes commands and names. When stdin and stderr are terminals and `TERM` is not `dumb`, input occupies a region immediately after the existing output, moving toward the screen bottom as needed, with a rule above and below and a status row (plan mode, model/effort, Auto and known context use). `NO_COLOR` keeps plain rules; below 20 columns only input is shown. Submit leaves a framed block in scrollback and restores the empty region. Pickers replace its input rows and restore input on close; workspace consent first discards pending input. The terminal stays raw while a region is active, including during a turn: typed keys edit the next input, Enter queues one next submission, and Ctrl-C cancels the turn. At an idle prompt Ctrl-C clears the line and a second within two seconds exits; Ctrl-D exits. `/edit` tears down the region and restores cooked mode while the editor owns the terminal, then redraws it.

Commands: `/plan [text]`, `/model [model] [fresh]`, `/effort [n|name]`, `/auto [on|off]`, `/status`, `/context`, `/compact [-v] [focus]`, `/friction`, `/trace`, `/reset`, `/edit`, `/help`, `/exit`. Only `/compact` makes a model request on its own; `/friction`, `/plan <text>` and a message composed with `/edit` are ordinary turns. Unknown commands are explained locally.

`!command` (one line) runs through `/bin/sh -c` in the active root with the exec environment allowlist, empty stdin, no timeout and Ctrl-C to cancel. It is the human acting: no mode needed, no model turn, nothing blocked. Output streams and is recorded (bounded by `MaxResultBytes`) as a shell entry sent as user text with a fixed preamble.

**Plan mode** is user-chosen and only removes authority. `--plan`, `/plan` (toggle) or `/plan <text>`, or a user message containing `/plan` as its own word outside code, turns it on; only the user turns it off. Dispatch refuses write and exec tools with a `plan_mode` outcome before `tool.started` (launch `--read-only` refusals stay `permission_denied`; unknown names are `tool_unavailable`); tool declarations and instructions do not change. User messages sent in plan mode carry a fixed plan-mode text part after the snapshot; the first message after it ends carries an ended marker; markers live on their entries and are never rewritten. A completed plan-mode reply whose last `<plan>` block has exact-line tags offers a picker — Implement here, Implement fresh (reset, then send the handoff text from `docs/reagent-plan-mode.md` §5 plus the plan), Keep planning (default). Implement here turns plan mode off and sends `Implement the plan.` in the same session; Implement fresh turns it off before resetting. Only ↑/↓/Enter act on the picker; any other key keeps planning. Without a terminal, chat prints a hint and starts no turn.

**Pickers** for `/model` and `/effort` open on a terminal; arrows or `j`/`k` move, Enter or a digit selects, Esc/`q`/Ctrl-C/Ctrl-D cancel; a read may hold several keys, decoded in order. Without a terminal, the commands list choices and take a number or name.

### 10.4 Context, compaction and model switches

The catalog's context window gives `/status` and `/context` a meter: the last attempted request's input tokens as a share of the window. After a turn at ≥ 60%, chat suggests `/compact`; at ≥ 80% the next message first compacts automatically (this between-turn trigger never fires mid-turn, blocked, empty, scripted or with an unknown window). An automatic failure sends the message anyway and disarms auto-compaction until a successful `/compact`, `/reset` or model switch; cancellation stops the message. A session blocked by any `limit_exceeded` is offered only `/reset`, since after a real overflow a compaction request cannot fit; `/compact` remains allowed.

**Within-Run continuation** is opt-in with `--in-run-compact` (off by default for both `run` and `chat`, retained on chat resume), overriding v1 §2.2's automatic-compaction exclusion at this boundary only. After all accepted calls have terminal results, a known-window model may summarize completed history before the next request when its last reported input or the estimated next input reaches 40% of the window. Use the §10.4 admission rate (measured input tokens per encoded byte × 1.5, minimum 0.25; 0.5 without a measurement) and reserve 16,000 tokens. Count the summary as a model step and account usage even on failure; require a follow-up step and at most eight successful transitions per Run. Preserve the submitted task and plan marker as an exact user entry in the Session alongside the summary; the summary must retain stage, constraints, unresolved findings/effects, exact artifact references, verification evidence and remaining work. Reject blank or over-32-KiB summaries and a handoff whose projected next request exceeds 40% of the window. If the summary cannot be attempted or accepted, trace why, disarm further attempts in this Run, leave accepted history intact and send the ordinary next request without a new admission limit; the provider still reports an actual overflow. The conservative estimate and reserve constrain summary attempts only, never an ordinary request after compaction was skipped. A failed summary model request with `provider_error` or `cancelled` stops as resumable, as no response was accepted; it never replays a tool. Success atomically replaces completed history, traces the transition in the same run and clears the last-request meter; it does not reset budgets, seen call IDs, authority, grants, effect records or verification state. Unknown windows or usage do not trigger speculative compaction; actual provider overflow remains an explicit limit blocker. Ordinary chat without the flag retains its 60% warning and 80% between-turn trigger.

**`/compact [-v] [focus]`** (not in a scripted chat) sends one request: unchanged instructions and tools, the current history view, and a temporary user entry with the embedded handoff prompt (plus `Focus:`). The reply must be text only and nonblank. Success replaces the whole history with one summary entry (text, replaced count, model), keeps session ID, seen call IDs and plan mode, clears blocking and the last-request meter, and is sent as user text with a fixed preamble. Any failure leaves the session unchanged. Each attempt has its own trace; the spinner shows progress.

**`/model <n|name>`** switches without a model request. The Session keeps its history (native items included), IDs, blocking, grants, plan markers and usage; only provider, model, default effort and the outgoing view change. The outgoing view renders all accepted entries into one fixed-order JSON-escaped historical user-text block behind a fixed preamble saying it is evidence, not instructions, and that recorded calls are not to be repeated (tool and shell records labelled `trust: untrusted_tool_data`), counting omitted native items; output after it continues natively. Repeated switches rebuild from accepted entries. Refuse unknown entries, unmatched batches, uncertain effects, unknown destination windows, and handoffs over the admission estimate: measured input tokens per byte of the last request (excluding native reasoning bytes) × 1.5, minimum 0.25, or 0.5 when unmeasured or across providers, plus 16,000 tokens headroom. The measured rate is set only by a successful generation and cleared by reset, successful compaction and any model change, not by an effort change. A refusal offers `/compact` then `/model`, or `fresh`, which discards history. Choosing the current model is a no-op. An effort change keeps the conversation.

### 10.5 Workspace tools

`request_workspace_access(path)` and `switch_workspace(path)` are read-class tools taking one absolute path. Each must be the only call in its response, otherwise every call in the batch is `not_executed`. Access to an unapproved destination needs the human: chat pauses activity and opens a picker (Allow for this session / Deny, Deny selected, no typing shortcuts) after discarding pending input and showing the escaped canonical path, existence, mode, plan restriction and disclosure. If pending input cannot be drained, consent is refused; piped input is never read as consent and gets no disclosure. After the picker, cancellation is rechecked and the destination re-resolved; a change is `workspace_validation_failed`. Denial or cancellation is `permission_denied`; no interactive terminal is `permission_required`; neither blocks. `--allow-workspace` preapproves exact paths. Grants last until chat exits, across reset, switch and compaction. A switch stages selection, tool bindings, project instructions and any grant, then commits all or nothing, and returns a fresh snapshot. Model prose, `AGENTS.md` and Git identity never grant access.

### 10.6 Auto routing

Optional, off by default: `--auto` or `/auto on`. `/auto off` or an explicit model/effort choice pins the current pair. Rejected with `--scripted` and `--show-context`. With no `--provider`, `--model` or `REAGENT_MODEL`, the fallback is `gpt-6-sol` (effort `medium` unless `--reasoning-effort` is given); otherwise the configured pair. Enabling is refused unless the fallback is catalog-known with a known window, a supported effort, and a credential or proxy; `/auto on` captures the current pair. Reset keeps Auto and zeroes router accounting. Adds no model instructions or tools. The README describes the routing endpoint and what is sent. `/auto on` discloses these details when enabled interactively; `--auto` adds no startup routing banner.

**Router.** TypeSafe Jev, `POST https://api.typesafe.ai/v1/systemone`, pinned to `jev-1.13.0`, one Choice question over 2–8 catalog pairs. Request ≤ 32 KiB, response ≤ 16 KiB, two-second deadline, one attempt, no redirects, status-only errors. Validate version, choice, probabilities (complete, summing to 1 within half a hundredth per choice for rounding) and usage. The packet and raw response are never traced.

**Candidates.** `gpt-6-luna` and `gpt-6-sol` at low, medium and high, plus the configured pair (and its high pair for another model), when catalog-known with a known window and a credential or proxy. Each route is admitted only if its full destination request is encodable and fits the §10.4 admission estimate. Model changes happen only at user-turn start; within a run only the current model's efforts are candidates.

**Packet.** Deterministic, built from accepted state: workspace, mode, plan setting, current route, project instructions, every summary and the latest user request whole, earlier user requests, the latest complete plan, and the latest assistant/tool/shell segment, then older noncritical entries newest-first. Noncritical text uses 512-byte previews with byte-count markers. If it does not fit, earlier user requests yield oldest first, to previews then to counted omission. Native items are omitted and counted. If the rest still does not fit, no routing call is made.

**Decision.** Route at each user-turn start, every three completed generations, and on new tool failures other than permission, `plan_mode` and `not_executed` outcomes. Order admitted pairs by cost: `gpt-6-luna`, then `gpt-6-sol`, then any other configured model; effort in catalog order within each. Sum Jev's probabilities from the cheapest; take the first pair reaching 0.80. Fall back only without a valid decision (router error, missing key, packet that cannot be built, fewer than two routes): the configured pair at turn start, the current pair mid-run. All but the last also end routing for the run, as do reaching the switch limit and a history that cannot be projected (unresolved batch, uncertain effect). At most three route changes per run; a change dwells three generations unless a tool failure selects a higher pair. A route change stays inside the Run: no new trace, Session or Run, no clearing of seen IDs, blocking, budgets, usage or grants, and no tool replay.

**Accounting and trace.** Router usage is counted separately from generation usage (`router_usage`) and never priced as generation. `auto.route` records boundary, candidates and exclusions, probabilities, confidence, ladder and cumulative sums, the rule and threshold, Jev status and latency, packet size, hash and omissions, the action, and after each switch, the first generation's input and cached tokens.

### 10.9 Experimental `git_do`

`--git-do jev|recipe` registers `git_do` (exec class, so read-only and plan mode withhold it); off by default and not saved for `--resume`. It carries out one of twelve fixed git recipes and returns proof: `status`, `explain_branch`, `pr_status`, `commit`, `split_commits`, `amend`, `commit_push`, `ship_pr`, `follow_up_pr`, `new_branch`, `rebase_push`, `revert_pr`. Optional arguments: `message`, `title`, `body`, `branch`, `pr`, `commit`, `paths`; Jev mode also accepts `recipe` as a non-binding model second opinion.

A call snapshots the root with git and `gh` (branch, default branch from `origin/HEAD`, upstream and divergence, up to 50 changed paths, 8 recent commits, and the branch's open pull request; a merged or closed one is reported separately) and removes the recipes that state does not allow. With `recipe`, the model names one and a disallowed one is declined. With `jev`, the model sends `intent` in English and one Jev request asks two choice questions: the outcome among the allowed recipes plus `none`, and whether the request also asks for non-git work. `none`, unfinished non-git work, or a Jev failure declines; mentions of changes already made are git-only. For a changing recipe, also decline when Jev assigns at least 0.3 probability to unfinished non-git work, even if it chose git-only; read-only recipes do not use this uncertainty veto. For a feasible outcome, the minimum probability is 0.7 for read recipes, 0.85 for most changing recipes, and 0.9 for `rebase_push` and `revert_pr`. A model recipe named in the optional argument or at the start of `intent` as `recipe_name:` lowers the bar to 0.7 only if it is offered and matches Jev's top outcome, except `rebase_push` and `revert_pr`, which always need 0.9; disagreement or an infeasible name requires 0.9, and no name overrides scope or `none`. Remove a leading recipe prefix before any Jev question, so the model's guess does not prime Jev's independent outcome, scope or revert-target choices. A branch name missing from `branch` is read from `intent`; a revert without `commit` asks Jev to choose among the recent commits, needing 0.9. Declines give actionable guidance: restate or name a likely recipe when confidence is low, clarify that work is already done for scope, and use `exec` when no recipe fits.

Every executed call returns a compact `decision` in its result data: the recipes offered after pruning (including `none` in Jev mode), the full Jev probability distribution for each question asked (`outcome`, `scope`, and `target` when needed), or `chosen_by: model` in recipe mode; the applicable confidence threshold, the model-named recipe and whether it agreed with Jev when present, the declining rule when one applies, and the same serialized repository snapshot Jev received. The Jev/result snapshot includes at most 12 changed paths (with `changed_count` giving the total number of porcelain entries, even beyond the 50 retained for recipes) and shortens recent commit lines to 80 characters; recipes retain the full collected lists. A Jev failure still reports the snapshot, offered recipes and `jev_error`; a decline inside a recipe reports `recipe`. Keep the typical added result below about 2 KB. `bench/git/harvest_git_do.py` extracts intent, arguments, snapshot, decision, status, session ID and run ID from trace JSONL files, warning and skipping malformed lines.

A recipe runs commands in the root with the exec environment, each with a 60-second timeout, and stops at the first failure. It never touches the default branch on the remote: pushes are `-u origin <branch>` or `--force-with-lease`, a branch is created only if `git check-ref-format --branch` accepts it and it does not exist, `new_branch` leaves it without an upstream, and a conflicting rebase is aborted. On a branch whose pull request is merged or closed, `ship_pr` fetches and starts a new branch from the default branch carrying the uncommitted changes (git refuses, changing nothing, if they conflict); it declines if the branch has commits that pull request lacks, and `follow_up_pr` is not offered. For `commit`, `commit_push`, `ship_pr`, `follow_up_pr`, and `amend`, optional `paths` names workspace-relative files or directories to commit when the tree has unrelated changes; reject absolute, parent traversal, missing (unless tracked and deleted), or escaping paths. Stage with literal pathspecs and decline if the index already holds changes outside them. Without `paths`, stage all changes as before. Before any staging, decline on untracked embedded repositories or worktrees (directories containing a `.git` file or directory) in the staging scope, naming them and advising `paths` or moving or ignoring them; `split_commits` also declines before its first commit. Record bounded `git diff --cached --name-status` after each add and reject any newly staged gitlink not previously tracked before committing; existing tracked submodules remain allowed. With `paths`, unrelated changes remain in the working tree, so check the index rather than requiring a clean tree. Afterwards it checks its result (remote tip equals HEAD, pull request open from the branch, clean tree or index for scoped commits, commit counts) and reports `done`, `unverified`, `declined`, `failed`, or `timeout`, with every command, its exit code and the last 1,500 bytes of its output. Effect is none when nothing ran, applied when commands ran, and unknown on a timeout, which stops the run as in §9. Jev calls and tokens are reported in the result, not as generative usage.

`make git-do-eval` evaluates trace-derived JSONL cases with reconstructed historical snapshots separately from hand-written cases, including finished-work, fresh mixed and misleading-prefix requests. Real calls are assigned by SHA-256 of call ID (first byte odd = held-out, even = tuning), fixed in the data file before threshold changes; never tune on held-out calls. Repeat each case five times by default (`N` overrides); `SET=tuning` runs only real tuning and handwritten cases, while `SET=held_out` runs only held-out real cases for the final check (`SET=all` runs both). `MODE=jev` queries live Jev; `MODE=recipe` uses a recipe explicitly named by the model in a captured intent and skips cases with no observed name, never inventing one from the label. Neither mode executes a recipe. Report right-and-ran, false declines, wrong-and-ran, and cases whose answers changed between repeats, per group and set; findings name the intent, outcome probability versus threshold, and scope probability. The evaluator and tool use the same recipe-selection and decline rules. Fail on any wrong-and-ran repeat or under 90% right-and-ran on held-out real git-only attempts. Older calls without decision logging carry reconstructed snapshots marked as such, not asserted exact historical Jev inputs.

## 11. Design fork: native versus prompt-defined tools

v0 uses native function calling. A prompt-defined grammar (catalog and JSON response format in the instructions, parsed locally, local call IDs, results as labelled data messages) is an optional experiment on a branch, never a launch flag.

## 12. Providers and the model interface

The v1 §5.1 interface separates orchestration from model I/O; it is not a provider-neutral conversation. Each provider adapter is an encoder, a decoder and headers over one shared transport (§6, §6.2). Native items stay provider-tagged and are never continued by another provider; crossing providers or models happens only through §10.4's text projection, at a turn boundary. No universal transcript type.

## 13. Status and verification

The v0 milestones (mechanical loop, read tools, visible context, live model, one edit, run a check) are complete; further work follows the plan or prompt in hand.

`go test ./...` is offline: scripted models, `httptest` servers, temporary directories. A test that reaches the internet is a bug. Adapter tests compare preview bytes with live-path bytes and cover retry, nonretryable failure, timeouts, native continuation and incomplete output. `make check` runs gofmt, vet and tests. `make tty-check` drives the built binary through `bench/tty`'s scenarios in a pseudo-terminal with an independent emulator, checking screens and that output arrives whole; it is offline and required evidence for terminal input or display changes. `make live` runs the opt-in live conformance tests per provider whose key is present; live Jev tests need `REAGENT_JEV_LIVE_TESTS=1` and human approval each time. Never claim a live run that did not happen.

For evaluated repository tasks, `docs/reagent-requirement-discovery.md` defines optional discovery and a small external, offline observation comparator. Reference build/test evidence and evaluator cases live outside candidate-writable output; a missing or failed reference check invalidates evaluation. This narrows §14's evaluation exclusion for comparison of already captured records only. It adds no production tool, candidate-execution sandbox, model-generated requirement map, or general task runner. `completed` remains an observation, not verification (§3).
