# Autonomous repository tasks — plan for #47–#50

This plan records issue scope, **not current v0 behavior**. `docs/reagent-v0-design.md` states what is implemented: #50's exec process-group handling is in §9, and within-Run continuation is specified in §10.4 for #49. Synchronous read-only child runs are now governed by v0 §3; executable review remains excluded. Implement each issue separately, amending the governing v0 section in place when the capability lands. Where a change reverses v1 §2.2's subagent or automatic-compaction exclusions, say so explicitly in v0. No workflow DSL, general sandbox or Rust-specific mode.

## #47: lightweight task contract

For a task that warrants it, plain-text instructions state the objective, behavior to preserve, intentional changes, scope, permissions, phases, verification commands, reviewer count, resource limits and stopping conditions. Ordinary small tasks need no staged process. Discover requirements from source and tests; when tests-first is required, make a meaningful tests checkpoint before substantive implementation. Use only warranted artifacts: a requirements-to-tests map, exact checkpoint references, independent findings with dispositions, and final evidence including failed or skipped checks. For evaluated tasks pin the controller and target revisions at launch; note known baseline bugs and spec/code disagreements instead of treating every old behavior as normative. Runtime `completed` is not verified success (v0 §3); missing required evidence, skipped/failed required checks or unresolved blocking findings prevent a verified claim.

Whether a user authorization of a multi-stage objective changes the shared `AGENTS.md` one-milestone stop rule is a **separate policy decision**. This plan does not change that instruction or grant permission to spend on APIs, publish, merge or run the Rust trial. Children, compaction text and project files cannot widen launch authority, plan/read-only restrictions or workspace grants.

## #48: bounded fresh-context child runs (shipped in v0 §3)

Validate existing Session, Trace and Workspace mechanics before adding a primitive. A synchronous one-level child starts a new Session with fixed runtime/project rules, explicit task/specification and an approved fixed code/test/evidence snapshot only: no parent transcript, native provider items, compaction handoff, author's reasoning or sibling findings. Inspect initial encoded requests with contamination canaries. Shipped #48 children are read-only. Executable review is deferred: a disposable copy alone cannot confine `exec` or justify a stronger authority claim. Keep provider credentials inside trusted adapters, never child tool arguments or reports. Return terminal status, bounded findings/summary, report reference and snapshot/trace identity; absent report, refusal, failure or exhaustion is not approval. Bound count, depth, aggregate calls/attempts/usage and work, propagate cancellation, complete cleanup, and never reset budgets silently. Test ordinary non-review use, two independent reviews, permission denial, malformed result, failure, exhaustion, cancellation and isolation offline. v0 §3 and §14 govern the narrow override of v1's subagent exclusion.

## #49: within-Run continuation (proposed)

Extend existing compaction at a pre-request boundary after every accepted call has a terminal result. Reserve summary/handoff/output space; handle unknown or inaccurate window/usage conservatively and stop with an explicit blocker on failure rather than loop. Preserve immutable task, constraints and authority outside lossy summaries when needed; retain stage, unresolved findings and uncertain effects, exact artifact/checkpoint references, verification evidence and remaining work. Reject empty or oversized handoffs. Failure leaves accepted history unchanged; success traces the transition without merging child histories or resetting budgets, call IDs, permissions or effects. No tool replay or crash-resume. Keep manual `/compact` and existing between-turn behavior. Force multiple boundaries and failure/cancellation in offline tests. Amend v0 §10.4 and explicitly override v1 §2.2's automatic-compaction exclusion only when shipped.

## #50: trustworthy command lifecycle (proposed)

First reproduce the static post-start `exec.ErrWaitDelay` classification risk. Track whether the process started; wait/capture failures after start cannot mean `process_start_failed` with no effect. On timeout/cancellation, terminate and reap supported-platform descendants within a bounded grace period; if cleanup or effects remain uncertain, report unknown and never retry. Confirm explicit timeouts longer than the 120-second default remain cancellable, preserve bounded stdout/stderr metadata and the environment allowlist, and use ordinary disk artifacts for long build/test logs where possible. Test exits, start failure, timeouts, cancellation, inherited pipes, large output and descendant cleanup on declared platforms. Amend v0 §9 and §14 when implemented; do not introduce a general job manager.

The Rust-specific acceptance and pilot live in `docs/reagent-rust-challenge.md` and issues #54/#46; neither is a baseline implementation recipe. The baseline should also work for an ordinary behavior-preserving repository refactor.
