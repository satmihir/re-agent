# Optional tests-first and independent-review workflow (#52)

Use this only when an authorized task contract calls for staged verification. Ordinary edits still need only proportionate checks. This is a procedure over existing file, exec and read-only `child_run` tools, not a scheduler, new runtime tool, or authority grant. `docs/reagent-requirement-discovery.md` governs the agent-produced requirements-to-tests map and independent behavior comparison. A runtime `completed` reply never certifies the task (v0 §3).

## Procedure

1. The controller records the objective, scope, behavior to preserve/change, launch permissions, stopping conditions, pinned reference revision, whether tests-first is required, required checks and reviewer count **before** work. It keeps the contract and independent evaluator outside the candidate-writable tree. Discover requirements and gaps from source and tests, not an evaluator's hidden cases. Simple tasks need no staged contract.
2. When tests-first is required, add executable behavior tests and only declared minimal scaffolding, before substantive source changes. Capture a tests checkpoint: paths, roles (`source`, `test`, `scaffolding`), byte digests and modes, plus a command/log showing these tests fail against absent or wrong behavior (`wrong_behavior`), or pass against a protected reference (`reference_pass`). A compiler/import failure alone is not evidence of a meaningful red test. Source files named in the pinned reference must be unchanged at this checkpoint. Do not count model prose as a test run.
3. For a required review gate, call `child_run` once per declared reviewer, sequentially, using **separate** child Sessions and the *same* fixed review file snapshot. Include the full checkpoint identity and exact task/spec in each child task, and tell reviewers to use severity labels `blocking`, `critical`, `high`, `major`, `medium`, `minor`, `low`, or `info`; label ambiguity is treated as blocking by the checker. Give reviewers factual source, tests and evidence—not parent transcript, author rationale or another reviewer's findings. Capture each child's status, bounded report, trace identity and snapshot ID. A refusal, invalid/missing report, exhaustion or absent trace is not approval. Read-only reviewers cannot execute tests; give them factual command logs from the checkpoint.
4. Record every finding with its reviewer Run ID and finding index. Fix blocking findings, explicitly disposition nonblocking ones with reasons, rerun affected checks on changed bytes, and repeat affected reviews on a *new* checkpoint. Never transfer approval to edited source or tests. A changed test expectation needs an explanation and a fresh tests checkpoint with fresh reviews. Disagreement is recorded, not decided by majority vote. If the four-child-per-parent-Run limit is exhausted (v0 §3), stop with a blocker; never reset budgets inside that Run or claim verification. A further authorized Run can collect additional reviews.
5. Freeze the implementation checkpoint and final candidate file manifest, obtain the required fresh implementation reviewers, then run every declared final command on that exact snapshot and retain argv, exit status, log and its digest. If behavior comparison is required, retain #51's independent `pass` report for that snapshot. Missing/skipped/failed commands, stale checks or unresolved findings prevent a verified claim.

## Offline evidence check

`python3 -m bench.workflow --contract CONTRACT.json --evidence EVIDENCE.json --candidate-root CANDIDATE --out REPORT.json` reads records; it **never runs** a candidate, tool, reviewer or model. All contract, evidence, review traces and logs and the report must be outside `CANDIDATE`. The script checks record structure and digests, not whether a test really asserts the right behavior, a reviewer is sincere, or the producer captured every file. Only an independently controlled producer and protected evaluator can establish those facts (#53). Its success status is `evidence_complete`, **not** task verified. Missing, corrupt, inconsistent or stale evidence returns `incomplete` and a nonzero exit.

The controller-owned contract (`version: 1`) has `task_id`, full `reference_revision`, nonblank `objective`, `tests_first: true` (this checker applies only to tasks requiring that gate), `reviewers_per_gate` (0–4), `reference_files` (`path`, `sha256`), `scaffolding_paths` (declared path list), `required_checks` (unique `id` and exact `argv`), and `comparison_required` (boolean). The candidate evidence (`version: 1`) repeats task ID and revision, records `run_status` as an observation only, refers to a digest-checked requirements map, and supplies ordered `checkpoints`, `reviews`, `dispositions`, `checks`, `final_snapshot_id`, `final_tree` and, if required, a digest-checked #51 `comparison` report. `run_status: completed` never substitutes for missing or failed evidence and does not mean verified success.

Checkpoint `files` are unique relative paths with `role` (`source`, `test`, `scaffolding`), numeric `mode`, and byte `sha256`. A checkpoint `snapshot_id` is SHA-256 of the sorted files encoded as compact sorted-key JSON; it is a scoped checkpoint identity, **not** a proof of complete-tree capture. A tests checkpoint also has `proof` (`kind`, exact `argv`, `exit_code`, digest-checked `log` attachment, nonblank `reason`). Each reviewer records `gate`, full `checkpoint_id`, the smaller fixed `child_snapshot_id`, `review_files` (`path`, `sha256`), distinct `session_id` and `run_id`, a digest-checked child trace and the actual `child_run` outcome data (`status`, `report_valid`, `snapshot_id`, `report`). Review files are a subset of the checkpoint. All reviewers at one checkpoint must have identical review files and child snapshot ID; a child trace must begin from empty history, show exactly one initial user entry naming both identities and end in a completed result. The `child_snapshot_id` is the #48 digest of the ordered review files (`len(path UTF-8):path:sha256` followed by LF for each file). Findings are addressed by `(run_id, index)` with `decision` (`fixed`, `accepted` or `unresolved`), `reason` and, for fixes, a later checkpoint identity. A blocking finding may only be fixed on a *later* checkpoint; every finding needs a disposition. A `no_findings` verdict may include nonblocking notes; any blocking finding requires `concerns`. The latest tests and implementation checkpoints need the declared count of independent, valid reviews with no blocking findings.

A final check records the contract check `id`, `checkpoint_id`, exact `argv`, `exit_code` and a digest-checked `log` attachment (`path`, `sha256`). `final_tree` repeats the final checkpoint identity and file manifest; the external producer must also retain staged/untracked files and deletions, since this checker cannot independently attest a complete tree. Test file digests must match between the latest tests and implementation checkpoints; if tests changed after an earlier tests checkpoint, an explicit `test_changes` entry (`path`, `from_checkpoint_id`, `to_checkpoint_id`, `reason`) and fresh tests reviews are required. The #51 comparison, when required, must report `pass` and name the final checkpoint as `candidate_snapshot`. Unknown or missing evidence fails closed. These structural checks cannot substitute for a human's disposition of semantic test quality or live model behavior.

Offline regressions create synthetic records for the ordinary-refactor and migration-shaped evaluator cases in `testdata/behavior/`: two fresh reviewers at both gates, and deliberate missing reviews, false final replies, weakened/stale tests, unresolved findings, missing logs, altered snapshots and incomplete comparison reports. They do not run the full Rust trial, spend on an API or claim independent live reviews.
